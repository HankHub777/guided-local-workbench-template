# Architecture decisions

Record only decisions that constrain future work.

## ADR-001: Start with local JSON read models

- Status: Accepted
- Context: Early office tools need fast iteration and normally have a spreadsheet source of truth.
- Decision: ETL produces validated JSON; the browser reads it through a data adapter.
- Consequence: Concurrent editing, authentication, and durable write workflows are out of scope until an explicit upgrade decision.

## ADR-002: Make chatbot-guided local workbenches the primary template use case

- Status: Accepted
- Context: Some enterprise environments allow users to use an LLM chatbot but do not allow agent capabilities. Ordinary users still need a safe way to create and evolve small local tools.
- Decision: Keep project context, file ownership, and verification steps in short repository documents that can be supplied to a chatbot. Design the initial tool to run locally without agent capabilities at runtime, while retaining the documented path to managed and product modes.
- Consequence: Documentation and small reviewable changes are first-class template features. Chatbot output must be reviewable locally, and no secrets or sensitive data may be included in chatbot context.

## ADR-003: Treat repository context as a portable handoff package

- Status: Accepted
- Context: A working single-file prototype may depend on one user's chat history or a particular model's temporary context. This makes it difficult to move work between people, LLMs, controlled agent environments, and engineering teams.
- Decision: Keep the project's intent, file ownership, data contracts, validation expectations, and upgrade triggers in versioned repository documents. Prefer small, reviewable changes that preserve these boundaries.
- Consequence: The template adds some initial documentation work, but a chatbot-only prototype can later move to a controlled agent environment or engineering ownership with lower communication cost and less reverse engineering.

## ADR-004: Ship default frontend design rules as template contract

- Status: Accepted
- Context: A separate, mature project (a static HTML/CSS/SVG report-generation pipeline) had already worked out and human-approved a set of general-purpose frontend visual rules — typography scale and line-height ranges, WCAG contrast targets, an 8pt spacing grid, CJK/Latin mixed-script spacing, table styling conventions, and image fit/crop priority. Its per-page human-approval gate workflow, fixed-canvas page-zone layout, and numeric-value approval-tier system are specific to one-shot slide/deck production and do not fit this template's iterative, small-change model — only the underlying visual rules generalize to a responsive `web/` application.
- Decision: Add `ai/DESIGN_RULES.md` as a new canonical file, sibling to `ai/ARCHITECTURE_RULES.md`, so every workbench built from this template starts with the same frontend defaults and an ordinary UI change cannot silently rewrite them. Register it everywhere `ai/ARCHITECTURE_RULES.md` is already registered: `docs/TEMPLATE_BOUNDARY.md`'s canonical list, `docs/FILE_MANIFEST.md`, `AGENTS.md`'s read-before-editing and template-contract rules, `README.md`/`README.zh-TW.md`'s template-contract list, `scripts/apply_update.py`'s `CANONICAL_PATHS`, and `scripts/build_context_bundle.py`'s `BUNDLE_FILES`.
- Consequence: A new clone's chatbot/agent session gets these frontend defaults automatically via `LLM_CONTEXT_BUNDLE.md`, without needing to reference the originating project. Individual tools may still deviate from any specific value; a deviation beyond a small tuning tweak should be logged here, the same as any other architectural decision.

## ADR-005: Split canonical docs into an always-bundled core and situational specialists

- Status: Accepted
- Context: PR #2 (`feat: extract reusable workbench engineering lessons`, merged 2026-08-20) added three new canonical files as engineering legacy from a real production instance built on this template: `docs/WEB_DATA_APP_DESIGN_PLAYBOOK.md`, `docs/ENTERPRISE_ENVIRONMENT.md`, and `docs/UPSTREAM_EXTRACTION.md`. They were correctly registered in `docs/TEMPLATE_BOUNDARY.md`, `docs/FILE_MANIFEST.md`, and `scripts/apply_update.py`'s `CANONICAL_PATHS`, but not added to `scripts/build_context_bundle.py`'s `BUNDLE_FILES`, and no ADR was recorded — leaving the omission looking like drift rather than a decision.
- Decision: Keep these three docs canonical but out of the default `LLM_CONTEXT_BUNDLE.md`; they apply only in a specific situation (building UI, enterprise network friction, upstream-porting a mature instance), not every session. Make discoverability explicit instead of relying on it being noticed inside an already-bundled file: `AGENTS.md` gained a "Situational guidance" section naming each doc and its trigger, and `scripts/build_context_bundle.py` documents the exclusion rationale in code.
- Consequence: The default bundle stays at its original 6 files as the canonical surface grows around it. A future canonical addition must explicitly decide "always-bundled core" vs. "situational specialist" and update `AGENTS.md`'s situational-guidance section accordingly, rather than silently landing in neither.

## ADR-006: Extract visual-quality rules from Monstrare (pjwang2022), not the workflow around them

- Status: Accepted
- Context: [Monstrare](https://github.com/pjwang2022/Monstrare) (pjwang2022) is a mature gate-based workflow layer for AI coding agents: Epic/User Story/Task decomposition, a 12-lane kanban board, 6 human review gates run partly by dedicated architect/security/test/UX subagents, cross-model routing, and a mandatory 5-stage "Epic 0" design-system ritual before any feature ships. It assumes full agent access and full-SDLC project scale. This template's primary persona has no agent access and builds one small tool through one acceptance-testable change at a time — importing that apparatus would replace the template's own change protocol with a heavier, differently-scoped one. Its `ai/skills/design-craft.md` and `ai/checklists/design-review-checklist.md`, however, contain visual-quality rules (interactive/data states, a grayscale-first workflow, a depth-pick-one-of-three discipline, Traditional Chinese font-stack/`lang` handling, and a discipline of comparing against curated real-product references instead of guessing values) that are genuinely useful independent of that workflow.
- Decision: Extract only the visual-quality rules, fold them into the existing `ai/DESIGN_RULES.md` and `docs/WEB_DATA_APP_DESIGN_PLAYBOOK.md` rather than adding new canonical files, and do not adopt the kanban board, review-gate/subagent apparatus, model routing, Epic/User Story/Task decomposition, or the 5-stage design-system ritual. `ai/DESIGN_RULES.md`'s Non-goals section records this exclusion and why, mirroring how it already records the Agent_html_report exclusions from ADR-004.
- Consequence: `web/` UI work gets a handful of concrete, previously-missing rules (states, depth, grayscale-first, CJK font-stack/`lang`, reference comparison) without adding a second workflow apparatus alongside this template's own change protocol, canonical-tier system, and `docs/DECISIONS.md`. If a future clone genuinely needs full multi-agent SDLC governance, that is a deliberate, separate template-level decision — not something this ADR pre-authorizes.

## ADR-007: Verification/QA scripts must survive enterprise networks and unattended terminals

- Status: Accepted
- Context: Three related gaps surfaced from real use. First, no canonical document told an LLM writing a verification/QA script for a specific change's acceptance criteria (AGENTS.md's Change protocol, step 3) that enterprise network friction — an authenticated proxy returning HTTP 407, TLS interception, DNS, or firewall blocks — must not be treated as proof the change itself is broken; `docs/ENTERPRISE_ENVIRONMENT.md` already carried this discipline for `scripts/check_environment.py`-style loopback checks specifically, but nothing generalized it to ad hoc verification scripts. Second, `scripts/apply_update.py` itself already had a related bug: after applying an update, it prints the "Paste this back into the chatbot so it knows what actually happened" block (README.md marks this step critical) and returns immediately with no pause, so a user who double-clicks the file loses that text when the console closes with the process. Third — the concrete, most common real shape of this problem — a chatbot asked for a QA/acceptance check for an instance project routinely produces a Python script plus a `.cmd` double-click launcher (e.g. `run_yield_workbench.cmd` wrapping `qa_yield_workbench.py`, printing a `[PASS]`/`[FAIL]` line meant to be copied back to the chatbot). Windows closes a `.cmd`-launched console the instant the batch file's last line finishes, independent of whatever the wrapped Python script does — so a pause added only inside the wrapped script does not reliably protect this shape at all; the launcher itself needs its own pause.
- Decision: Fix `scripts/apply_update.py` directly — add `pause_for_copy()`, which prompts for a keypress before exiting, called right after the must-be-copied block, and skips the pause when `sys.stdin.isatty()` is false so CI/automation/piped runs never hang. Codify three things as new non-negotiable rules in `AGENTS.md` (Core-bundled, so every session sees them regardless of whether the current machine happens to be restricted): a directly-run verification script's user-copied output must not be able to vanish before it's read (the `pause_for_copy()` pattern); a generated `.cmd`/`.bat` double-click launcher must end with its own native `pause` line regardless of what the wrapped script does, since that is the mechanism that actually protects this shape; and a verification script must not fail acceptance criteria solely due to environment network friction. Generalize `docs/ENTERPRISE_ENVIRONMENT.md`'s existing loopback-check discipline with an explicit "Verification scripts written for a specific change are not exempt" section, and add both the copy-safety and launcher-pause rules to `scripts/README.md`'s general script-authoring contract. Deliberately not implemented as a Claude-Code-specific Skill file: per ADR-006, this template does not maintain a separate governance track for agent-capable sessions, and a chatbot-only session (this template's primary persona) would never load a Skill — the canonical docs already reach every session type via `LLM_CONTEXT_BUNDLE.md`.
- Consequence: `apply_update.py` can no longer lose its critical handoff text to an auto-closing terminal. Every future verification/QA script an LLM writes for this template — canonical or instance, run directly or via a generated double-click launcher — inherits all three rules from `AGENTS.md` without needing a specific enterprise-environment trigger to surface them.
## ADR-008: Make docs/FILE_MANIFEST.md the single source of truth for bundle membership

- Status: Accepted
- Context: `AGENTS.md` treats `README.md` as template contract and points chatbot-only sessions to its "Working with an LLM chatbot" section, and its Change protocol step 4 requires checking `docs/UPGRADE_PATH.md`'s triggers on every request. Neither file had ever been added to `scripts/build_context_bundle.py`'s `BUNDLE_FILES` constant, so a chatbot working from only `LLM_CONTEXT_BUNDLE.md` was being told by `AGENTS.md` to follow rules it never actually received — the exact "canonical file landed in neither tier, looks like drift not a decision" failure mode ADR-005 named, recurring because the tiering decision lived in two places (`docs/FILE_MANIFEST.md`'s Canonical/Instance column and `scripts/build_context_bundle.py`'s separate `BUNDLE_FILES` list) that nothing kept in sync. Patching the two missing files would have left that root cause in place for the next canonical addition.
- Decision: Add a `Bundle` column (`Core` / `—`) to `docs/FILE_MANIFEST.md`'s "Always-present foundation" table and make it the *only* place this decision is recorded. Rewrite `scripts/build_context_bundle.py` to parse that table directly (`parse_bundle_manifest()`) instead of carrying its own `BUNDLE_FILES`/`BUNDLE_FILE_PURPOSES` constants — the file list and each file's one-line purpose both come from the table's Path and Why-it-exists cells. The parser hard-fails (refuses to generate a partial or wrong bundle) if the table's header shape changes, a row is malformed, or any row's Bundle cell is missing or not exactly `Core`/`—`, so an unclassified future row breaks the build loudly instead of silently landing in neither tier. `README.md` and `docs/UPGRADE_PATH.md` are marked `Core` under this scheme, since both apply to every request rather than a specific situation, per ADR-005's tiering rule. A second pass, prompted by a user review of this same table, also marks `docs/WEB_DATA_APP_DESIGN_PLAYBOOK.md` `Core`: this template's own README frames an ETL-to-React-frontend web data app as the default shape of nearly every tool built here, so "does this session touch UI" is closer to the norm than an edge case for this template specifically, unlike a generic project. `docs/MIGRATION_FROM_SINGLE_FILE.md` (and its `.zh-TW` translation) stays `—` on the same review — it is a one-time, binary, start-of-project fork (a project either began as a single-file prototype or it didn't), so it fails the "regardless of what the session is about" test even though it is a genuinely important entry point for the template's mission; instead, it is added to `AGENTS.md`'s Situational-guidance list, where it had been missing entirely despite the other three situational docs all being listed there.
- Consequence: The default bundle grows from 6 to 9 files (`README.md`, `docs/UPGRADE_PATH.md`, and `docs/WEB_DATA_APP_DESIGN_PLAYBOOK.md` added), and every chatbot-only session now receives the documents `AGENTS.md` already assumed it had. Adding, removing, or reclassifying a bundled file is now a one-line edit to `docs/FILE_MANIFEST.md`'s Bundle column — `scripts/build_context_bundle.py` never needs a matching edit, and cannot drift out of sync with the manifest the way it did before this ADR. A single-file migration is now discoverable from `AGENTS.md` itself rather than only from `docs/FILE_MANIFEST.md`'s "Read or update when" column.

## ADR-009: Visual guide case-study tabs need a distinct job each and a real reference implementation, not illustrative content

- Status: Accepted
- Context: `docs/visual-guide.html` (an onboarding artifact not yet finished, meant to eventually ship with the template) grew a "兩來源整合案例" (two-source integration case) tab to teach schema reconciliation through a worked example. On review, everything in it — schema tables, a reconciliation diagram, chatbot dialogue — was invented to illustrate the concept, with no real dataset, ETL, or running implementation behind it. Held against the standard set by commercial statistical software tutorials (JMP, SPSS, Minitab: a real dataset, a real scenario, a step-by-step walkthrough, a comparable real result at the end that leaves the reader with actual operational capability, not just conceptual familiarity), it falls short — closer to a mockup of a tutorial than an actual one. Visual Guide's own Steps 2, 4, and 6 already meet that bar with real screenshots from an actual build; the case-study tab does not. Separately, planning a second case-study tab (a single-source worked example) surfaced a positioning risk: without one clear, non-overlapping job per tab, multiple worked-example tabs read as redundant or coupled, defeating the mental map the guide is supposed to build.
- Decision: (1) Give each tab exactly one job, with earlier ground covered by cross-link rather than repetition: Visual Guide teaches only generic, data-agnostic mechanics; a new "Case 1: from one dataset to a complete demo" tab is the first full end-to-end worked journey; the existing two-source tab (renamed "Case 2: integrating two data sources" for the numbered sequence) teaches only the delta beyond Case 1 — reconciliation, contract, validation-rejection; the migration tab teaches only retroactive recovery from a pre-existing messy single-file prototype. (2) A case-study tab may not ship as illustrative-only content. Build a minimal real reference implementation for Case 1 first (real fixture data, a real ETL/contract step, a real running minimal frontend), author that tab's content from its actual artifacts, validate the pattern, then apply the same treatment to Case 2's existing content. Full architecture table, current build status, and ordered next steps are kept in `docs/VISUAL_GUIDE_ROADMAP.md` rather than duplicated here, since that detail will keep changing as the work progresses.
- Consequence: Case 2's current content stays in place as a known placeholder rather than being mistaken for finished — it needs replacement once Case 1's real-implementation pattern is validated. Case 1 does not exist yet and is the next priority. A future session with none of this conversation's history can resume correctly from `docs/VISUAL_GUIDE_ROADMAP.md` alone.
